1. Executive Summary & Architectural Overview

NinjaX Chase is a high-performance, single-threaded, browser-native 2D endless runner built purely on standard web technologies without external dependencies, build tools, or heavyweight game engines. The architecture emphasizes frame-rate independence, zero-allocation execution loops, sub-pixel parkour kinematics, and real-time digital signal processing (DSP) for audio synthesis.

Core Design Philosophy: Zero-Dependency Pure Engineering
By eschewing heavy frameworks (such as Unity, Phaser, or PixiJS), this codebase demonstrates absolute mastery over raw 2D coordinate spaces, hardware-accelerated rasterization pipelines, discrete input event queues, and temporal integration.

3. The Decoupled Game Loop & Temporal Integration

3.1 The Problem with Frame-Coupled Updates

In naive game implementations, movement is computed by adding a static pixel offset every frame: x += speed. This causes a catastrophic flaw: on a 60Hz screen, the player moves at 60 units/sec, but on a 144Hz or 240Hz gaming display, the player moves at 144–240 units/sec, rendering the game unplayable.

3.2 Delta-Time ($\Delta t$) Normalization & Clamping

The engine uses temporal integration based on the elapsed time between hardware frame ticks:

$$\Delta t = \frac{t_{\text{current}} - t_{\text{previous}}}{1000}$$

All velocity and acceleration vectors are multiplied by $\Delta t$, guaranteeing identical movement speed across any refresh rate.

function gameLoop(timestamp) {
  if (!lastTimestamp) lastTimestamp = timestamp;
  
  // 1. Compute delta-time in seconds
  const rawDt = (timestamp - lastTimestamp) / 1000;
  lastTimestamp = timestamp;

  // 2. Clamp delta-time to 0.1s max to prevent "Spiral of Death" and Tunneling
  const dt = Math.min(rawDt, 0.1);

  // 3. Discrete Phase Separation
  update(dt);
  render();

  requestAnimationFrame(gameLoop);
}
Interview Deep-Dive: Delta-Time Clamping
If a user switches browser tabs, requestAnimationFrame pauses. When returning 10 seconds later, rawDt would equal 10.0. Without clamping, applying $v \cdot 10.0$ would teleport the character through platforms (tunneling) and trigger immediate deaths. Clamping to $0.1\text{s}$ gracefully absorbs tab suspension.

4. Parkour Kinematics & Player State Physics

4.1 Variable Jump Boost & Gravity

To deliver a modern responsive feel (similar to Celeste or Vector), the jump mechanics implement a dual-phase impulse curve:

  1. Initial Impulse: When Jump is triggered on the ground, an instantaneous vertical velocity $v_y = -580\text{ px/s}$ is applied.
  2. Sustained Thrust Window: If the player continues holding the jump button, a continuous upward acceleration $a = -1100\text{ px/s}^2$ is integrated for up to $0.16\text{s}$. Releasing early terminates the boost immediately, providing precise analog control over jump height.
  3. Constant Gravitational Acceleration: Downward pull $g = 1550\text{ px/s}^2$ guarantees crisp falling arcs without floatiness.

4.2 Jump Buffering & Coyote Time

Mechanism Temporal Window Problem Solved
Coyote Time $120\text{ ms}$ Allows the player to execute a jump even after their feet have physically walked off a NinjaX ledge, preventing frustrating "I pressed jump right at the edge but fell!" deaths.
Jump Buffering $160\text{ ms}$ Stores jump inputs pressed slightly before touching down, executing the ground jump the exact millisecond the player contacts the NinjaX surface.

4.3 The Slide Hitbox Offset Problem (Crucial Bug Fix)

A classic game engineering pitfall occurs when toggling crouch/slide hitboxes. If a character standing height is $56\text{px}$ and slide height is $28\text{px}$, simply changing height = 28 without shifting y causes the hitbox feet to float $28\text{px}$ above the NinjaX surface! On the next physics tick, the ground check fails, causing the player to enter airborne gravity mode and slide off ledges prematurely.

// CORRECT Hitbox Height Transition (Preserving Ground Plane Alignment)
triggerSlide() {
  if (this.grounded && !this.isSliding) {
    this.isSliding = true;
    this.slideTimer = this.maxSlideDuration;
    // Shift Y downwards by height delta to lock feet to NinjaX surface
    this.y += (this.standHeight - this.slideHeight);
    this.height = this.slideHeight;
  }
}

// Recovery back to standing
if (this.slideTimer <= 0 && !input.slide) {
  this.isSliding = false;
  // Shift Y upwards to maintain ground contact
  this.y -= (this.standHeight - this.slideHeight);
  this.height = this.standHeight;
}

4.4 Mid-Air Double Jump & 360° Somersault Flip

When the player executes a second jump while airborne (!this.grounded && this.canDoubleJump):

  • The double jump token is consumed: canDoubleJump = false.
  • Upward velocity is reset to $v_y = -550\text{ px/s}$.
  • The somersault state is activated: isDoubleJumping = true, angular velocity $\omega = 14\text{ rad/s}$.
  • During rendering, a local 2D affine transformation matrix rotates the sprite about its centroid $(x + w/2, y + h/2)$ through $2\pi$ radians, smoothly returning to the upright posture upon completion.
  • The double jump recharges automatically upon touching any NinjaX platform.

5. Procedural Level Generation & Memory Lifecycle

5.1 Solvability & Dynamic Difficulty Scaling

To ensure endless playability without generating mathematically impossible jumps, gap widths are calculated dynamically as a function of the player's current horizontal scroll velocity:

$$G_{\text{gap}} \in [110, \min(260, 120 + v_{\text{scroll}} \cdot 0.22)]$$

Building height variance is constrained by $|\Delta y| \le 110\text{px}$, ensuring the parabola of any single or double jump can always reach the subsequent ledge.

Endless runners risk memory leaks and Garbage Collection (GC) frame stutter if objects are continuously instantiated and abandoned. The NinjaXManager implements active pruning and recycling:

6. Collision Detection Mathematics

6.1 Axis-Aligned Bounding Box (AABB) Intersection

NinjaX platforms, AC compressor units, and low overhead beams utilize 2D Axis-Aligned Bounding Box testing. Two rectangular hitboxes $A$ and $B$ intersect if and only if:

$$(A_x < B_x + B_w) \land (A_x + A_w > B_x) \land (A_y < B_y + B_h) \land (A_y + A_h > B_y)$$

6.2 Overhead Laser/Beam Slide Clearance

The overhead beam hangs between $y_{\text{NinjaX}} - 72\text{px}$ and $y_{\text{NinjaX}} - 36\text{px}$.

  • Standing Ninja ($h=56$): Span is $[y_{\text{NinjaX}} - 56, y_{\text{NinjaX}}]$. The interval $[y_{\text{NinjaX}} - 56, y_{\text{NinjaX}}]$ overlaps $[y_{\text{NinjaX}} - 72, y_{\text{NinjaX}} - 36]$ because $y_{\text{NinjaX}} - 56 < y_{\text{NinjaX}} - 36$. $\rightarrow$ Collision triggers fail.
  • Sliding Ninja ($h=28$): Span is $[y_{\text{NinjaX}} - 28, y_{\text{NinjaX}}]$. Since $y_{\text{NinjaX}} - 28 > y_{\text{NinjaX}} - 36$, there is zero mathematical intersection. $\rightarrow$ Player glides safely underneath.

6.3 Euclidean Distance vs Squared Distance Optimization

For circular collectibles (Coins and 2X Multiplier Orbs), collision occurs when the distance between centers is less than the sum of radii ($r_1 + r_2$). Computing Euclidean distance requires a square root operation ($\sqrt{\Delta x^2 + \Delta y^2}$), which is computationally expensive on older mobile CPUs. The engine compares squared values:

$$\Delta x^2 + \Delta y^2 \le (r_1 + r_2)^2$$

8. Senior Technical Interview Preparation: Deep-Dive Q&A

Q1 Why is it critical to separate update() from render() in game architecture?
Separating state progression (update) from drawing (render) adheres to the Single Responsibility Principle and is essential for deterministic simulation. If graphics rendering lags due to high GPU load, the physics engine can either interpolate or tick multiple small physics steps without dropping collision accuracy or altering gameplay physics.
Q2 What is the "tunneling effect" in high-speed collision detection, and how do we prevent it?
Tunneling occurs in discrete collision detection when an object’s velocity is so high (or frame rate drops so low) that its position delta $\Delta x = v \cdot \Delta t$ exceeds the width of an obstacle, causing it to teleport completely through the obstacle between frame $N$ and $N+1$. We prevent tunneling by clamping $\Delta t \le 0.1\text{s}$, using sub-stepping (dividing large frame deltas into smaller integration steps), or utilizing Swept AABB / Continuous Collision Detection (CCD).
Q3 How does the Finite State Machine (FSM) pattern prevent gameplay bugs compared to boolean flags?
Relying on multiple loose booleans (e.g. isPlaying, isPaused, isDead, isCountdown) leads to invalid permutation states (e.g. isPlaying = true AND isDead = true). An FSM enforces mutually exclusive, strictly guarded state transitions (e.g. START $\to$ COUNTDOWN $\to$ PLAYING $\to$ FAIL_SEQUENCE $\to$ GAMEOVER), ensuring that input listeners and collision checks only execute in their valid lifecycle contexts.
Q4 Why is object pooling and array recycling important in browser JavaScript games?
In JavaScript, continuously creating new objects (like bullets, particles, or buildings) and discarding them creates garbage on the heap. When the V8 garbage collector runs its mark-and-sweep cycle, it pauses the main execution thread (GC pause), resulting in noticeable micro-stutters and dropped frames. Reusing existing objects and filtering arrays in-place maintains a stable heap memory footprint.
Q5 How does parallax scrolling mathematically create the illusion of 3D depth?
Parallax depth relies on motion parallax, where objects farther from the viewer appear to move slower across the visual field than closer objects. By multiplying the world scroll speed by fractional scale coefficients ($k_{\text{distant}} = 0.08$, $k_{\text{mid}} = 0.28$, $k_{\text{play}} = 1.0$), each 2D background layer translates at an inverse rate to its simulated Z-distance, creating authentic optical depth.
Q6 How do you prevent OS keyboard auto-repeat from corrupting game input (such as accidental double jumps)?
When a user holds down a key, operating systems emit repeated keydown events at the OS repeat rate. In our input controller, we check if !input.jump before triggering the jump handler, setting input.jump = true. Subsequent repeat events are ignored until the key is physically released (keyup resets input.jump = false). This guarantees that a double jump requires a deliberate second physical key press.
Q7 How does procedural Web Audio synthesis improve application security and deployment simplicity?
Loading external sound files via HTTP fetch() or Audio() elements frequently encounters CORS origin restrictions when opening HTML files directly from local disk (file:/// protocol). Real-time mathematical synthesis via Web Audio oscillators operates entirely in memory with zero HTTP network requests, guarantees zero audio loading lag, and eliminates external asset dependencies.
